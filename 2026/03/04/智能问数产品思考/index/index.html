智能问数产品思考

关于智能问数（Text-to-SQL）产品的深度分析与未来展望

目录

  1. 背景
  2. 痛点
  3. 可能的解决方法

一、背景

当前方案

RAG + LLM Workflow 模式：

典型架构：

  • 检索层：向量数据库 + 关键词检索（混合检索）
  • 知识层：表、字段、术语、指标、纬度、纬度值、记忆
  • 生成层：大模型生成语义 SQL
  • 执行层：SQL 引擎执行和数据返回

我们目前还是第二个 RAG 阶段 + 我们的 Agent 平台里的 workflow（对话流、动作流）
原先我以为 用动作流的固化流程智能体可以提升问数的稳定性和准确性，但实际这种模式导致了现场架构流程调优、分析师结构化知识梳理、rag 检索优化，提示词优化的人工维护工作量的爆炸，9 张表七八百个问题自测知识积累和调优，花了非常多的人力才搞定平均准确率在 90%，但实际我们问数平台还有很多一本账中屏里的指标问不出来，还有人法信的几百张表都没有接入，对于客户来说我们的平台可问范围远远没达到要求。但我们目前这套架构模式知识实施治理的工作量是相对比较重的，而且对多表关联支持的不好。

二、痛点

1、知识维护成本高：需要人工梳理和维护较多的指标、术语、纬度值近义词，才能保证比较高的准确率
2、agent 流程维护成本高：需要专员调试修改对话流、动作流，同时还需要后端配合接口调试（动作流里都是接口技能）
3、组件化后对接成本比较高，统一元数据（中研院）、agent（中研院）、前端 太多团队对接协作，调试系统问题的成本很大
4、平台架构臃肿、落后，对 ai 不够友好，我们可以用 ai 来做动作流里的接口，但 agent 的对话流和动作流没有接口可以让 ai 自动去开发调整

三、可能的解决方法

方法 1：知识体系重构 + 自动化学习与治理

对应痛点：#1 知识维护成本高

核心思路：将知识从硬编码中解耦，构建可复用、可持续更新的知识体系

具体措施：

  • 知识图谱（本体）：建立概念定义和之间的语义关联，梳理本体元知识，解决术语、指标维护爆炸问题。
  • 标准化主题库：按住建、交易、政务业务场景建立标准的主题库，这样可以屏蔽每个地方或项目表结构和表数据的差异，保证积累的知识（本体、术语、指标）稳定可复用，但会增加从业务原始表到治理到主题库的数据开发工作量。
  • 自动化学习与治理：引入用户反馈机制，模型自动修正错误知识，减少人工维护工作量。模型每天自动总结问题，针对问不出来或者问出来有问题的进行自我总结，最后让人工来审核。比如客户问的问题超出了目前接入表的范围，有些指标超出了目前定义的指标范围，有些行业黑化无法理解需要添加新的术语，让模型被动接收我们分析师梳理的知识变成主动去学习完善自己的知识体系。
  • 简化知识定义：
    SQLBot 的知识维护和 RAG 检索也比我们目前的架构简单
    SQLBot 里只有 术语、表 Schema 描述（包含字段）、SQL 示例、历史相似提问、 这些知识来召回参与 SQL 生成，我们的问数系统里多了 指标、纬度、纬度值 ，指标在 SQLBot 里用术语可以代替， 纬度和纬度值在 SQLBot 里可以维护在字段描述里，可以明显对比出 SQLBot 参与 SQL 生成的检索知识维护比我们的平台要简单，所以他们在部署、快速导入大量表比我们的系统初始化效率要高，并且 SQLbot 通过维护表间关系支持多表查询，用少量的实施工作就能达到 80% 的效果，但也有一些后期扩展问题，SQLBot 在字段描述里添加纬度值的近义词非常麻烦，针对无限动态实体的纬度值需要人工去数据库里查了去字段描述里添加近义词，维护起来没有我们系统方便。只要客户问到 纬度值里近义词相关的问题 SQLBot 都需要非常麻烦的维护工作量，维护的模式没有我们系统方便。

方法 2：技术栈和架构重塑

对应痛点：#2 agent 流程维护成本高
#3 组件化后对接成本比较高
#4 平台架构臃肿、落后，对 ai 不够友好

核心思路：Python 后端 +Vue 前端，放弃公司框架和 Agent 平台

当前架构问题
⚠️ 架构过于复杂 - 多组件（问数系统、统一元数据、指标中心、Agent 平台）多团队，协作成本巨大，AI 无法全链路介入，Agent 平台没有给 AI 提供接口，直接限制了系统的快速迭代

⚠️ Java 不适合 AI 核心逻辑 - Java 也有 AI 相关的生态，但没有 python 生态那么完善，亲 AI

⚠️ Epoint 框架过于重量级 - 启动慢，很多框架的功能根本用不到

可以参考开源 SQLBot 技术栈来激进调整
Python 3.11 + FastAPI + LangChain/LangGraph + PostgreSQL/pgvector 做后端 AI 编排，Vue 3 + TypeScript + Element Plus + AntV 做前端交互，Node.js + G2 SSR 做服务端图表渲染，整体通过 Docker 单容器部署，本地开发使用 PM2 统一管理。

摒弃 Epoint 框架后会缺失一些有用的能力，比如统一支撑、统一用户、工作流引擎，需要用 AI 来补齐这块短板，把 SQLBot 里的 pgsql 业务库换成 国产化达梦库和 mysql 库， pgvector 就用 ES 全文 + 向量检索来替代，这个技术栈还有个问题，没有 java 的 write once run anywhere 跨平台那么强，nodejs 相关依赖打进 docker 都需要在不同国产化环境下进行，要做下面几点补齐适配

缺失能力补齐方案：

  • 统一支撑（权限、审计）：通过 LangGraph 中间件实现请求链追踪和操作审计，用 AI 自动生成权限模型配置，配合 FastAPI 的中间件实现细粒度权限控制
  • 统一用户认证：基于 OAuth2/JWT 的轻量级认证方案，结合 PostgreSQL（或达梦）的用户表，借助 FastAPI-JWT 实现
  • 工作流引擎：用 LangGraph 的状态机（State Machine）和 Agent 决策流程替代传统工作流，通过 AI 的 tool_choice 实现条件分支和流程编排，更加灵活智能

国产化数据库适配：

  • 达梦库（DM8）：SQL 方言接近 Oracle，改动主要在连接池（pymongo → dmPython）和 SQL 分页语法，LangChain 的 SQLDatabase 需要自定义 Dialect
  • MySQL：直接兼容，无需额外改动
  • ES + 向量数据库：ES 8.0+ 的 dense_vector 字段可替代 pgvector，全文检索 + 向量检索的组合甚至比 pgvector 更灵活，支持混合搜索

跨平台国产化部署方案：

  • 标准 Docker 镜像：构建 Python 基础镜像（包含必要系统库），Node.js 依赖通过 npm ci --only=production 在构建时确定版本，避免运行时变化
  • 分环境构建：针对飞腾 ARM、龙芯等不同 CPU 架构，预先构建多架构镜像（docker buildx）并推送到私有仓库
  • 动态链接库处理：对于国产系统特定的 C 扩展（如数据库驱动），在 Docker 构建阶段通过多阶段构建（Multi-stage Build）编译，确保兼容性
  • 本地开发：PM2 配置文件支持条件编译，通过环境变量区分不同 OS，开发机直接用 Host OS，避免频繁构建镜像

权衡与建议：

  • 相比 Java 的跨平台，这套栈的优势是 轻量灵活快速迭代 ，劣势是 国产化环境需要额外测试。建议早期在标准 Linux 环境验证，后期专项解决国产 CPU + OS 的适配

然后在 SQLBot 基础上进行 AI agent 的架构演化，目前我们智能问数和 SQLBot 都没有完全发挥模型的能力，模型既是智能体（Model is the Agent）

把生成 SQL 的固定流程换成 CC 这种智能体自主调用工具去完成，CC 可以去读取 MD 文件（提前把数据库里的术语、表 Schema 信息等信息 初始化到 md 文件里，或者我们新增采集这些信息的时候就不存库里直接存入 md 文件），然后我们同时也提供一些调用这些知识信息的接口，最后 CC 还能通过 SKills 或者 mcp 的方式连接上数据库自己去查询，我们原先的 LLM 方案是固定流程，LLM 模型只是在最后一步被调用来生成 SQL，并没有完成发挥 LLM 的自主规划、调用工具和 skill 的能力

相关详细设计：双方案切换详细设计

还有一种更简单的集成方案，快速把 SQLBot 的前端配置能力复制到我们现在的智能问数系统中，然后把 SQLBot 后端的生成 SQL 的接口当成一个服务 给到我们问数系统里，把 SQLBot 当成一个 SQL 生成的引擎来用

四、下一步计划

基于以上分析，建议分三个阶段推进智能问数产品的演进：

阶段一：快速集成验证（1 个月）⚡

  • 复制 SQLBot 前端配置能力到现有问数系统
  • 将 SQLBot 后端封装为独立服务
  • 实现问数系统与 SQLBot 的 API 对接
  • 在小范围内验证 SQL 生成质量

阶段二：知识体系重构（1-2 个月）

  • 梳理核心业务本体，建立术语、指标、维度的语义关联
  • 搭建标准化主题库，屏蔽不同项目数据源差异
  • 引入用户反馈机制，实现知识自动修正与学习

阶段三：架构演进与 Agent 化（持续）

  • 评估集成效果，决定是否全面迁移到 SQLBot 技术栈
  • 从固定 LLM Workflow 演进到 Agentic AI 模式
  • 集成 Claude Computer Use/Code Interpreter 能力
  • 实现知识库 MD 文件化 + 数据库查询的双通道模式

预期收益：

  • 快速方案：最小改动，快速验证 SQLBot 能力
  • 知识维护：工作量降低 60%+
  • 多表查询：支持能力显著提升
  • AI 自主决策：实现真正的智能 Agent
